# Disaster recovery

Module M9. This is the drill that justifies everything in
[backup-and-restore.md](backup-and-restore.md): it proves the backup restores
onto a machine that never had the application, and it produces a measured
recovery time instead of a guess.

## Measured result

| What | Time |
|---|---|
| Total VM loss → working service | **348 s (5 min 48 s)** |
| Deployment content restored and verified | **8 s** |

"Working service" means `curl http://192.168.122.12/labapp/health` returning
`200 OK app01` through the reverse proxy, on a VM rebuilt from nothing.

## The drill

Starting point: one verified backup pulled off the VM (`~/kvm-lab-backups`), and
`app01` running with the application deployed.

### 1. Total loss

```bash
virsh destroy app01
virsh undefine app01 --remove-all-storage --snapshots-metadata
```

```
Domain 'app01' destroyed
Domain 'app01' has been undefined
Volume 'vda'(/var/lib/libvirt/images/app01.qcow2) removed.

$ virsh list --all
 Id   Name    State
-----------------------
 2    web01   running
```

The disk file is gone. So is the `clean-deploy` snapshot, because a snapshot
lives on the same disk it protects - which is the whole point of the
snapshot-versus-backup distinction, demonstrated rather than described.

### 2. Rebuild the machine

```bash
bash scripts/create-vms.sh
```

`create-vms.sh` is idempotent, so it skipped `web01` and rebuilt only `app01`
from the shared cloud image - a genuinely fresh disk, not a repaired one. The
guest was reachable over SSH about 20 seconds later.

### 3. Configure it

```bash
ansible-playbook site.yml
```

```
PLAY RECAP
app01  : ok=18  changed=11  unreachable=0  failed=0
web01  : ok=17  changed=0   unreachable=0  failed=0
```

`changed=11` on app01 versus `changed=0` on web01 is the useful signal: the
playbook did real work on the blank machine and nothing at all on the untouched
one. Time to a working service: **348 s**.

### 4. Restore the deployment content

The rebuilt machine had Tomcat installed by the playbook, but the off-VM archive
is the independent copy, so it gets exercised too. Deployment destroyed on the
fresh VM:

```
$ ssh ops@192.168.122.11 'sudo rm -rf /var/lib/tomcat10/webapps/*'
through Apache now: HTTP 404
```

Then restored from the host-side copy, verified with the same tool that made it:

```
$ scp ~/kvm-lab-backups/webapps-2026-09-30_132943.tar.gz* ops@192.168.122.11:/tmp/
$ ssh ops@192.168.122.11 'sudo /usr/local/bin/tomcat-backup.sh verify /tmp/webapps-2026-09-30_132943.tar.gz'
RESTORE VERIFIED: 5 files match (/tmp/webapps-2026-09-30_132943.tar.gz)

$ ssh ops@192.168.122.11 'sudo tar -xzf /tmp/webapps-*.tar.gz -C /var/lib/tomcat10/webapps
                          && sudo chown -R tomcat:tomcat /var/lib/tomcat10/webapps
                          && sudo systemctl restart tomcat10'
content restored: 8s

health after restore: HTTP 200  body=OK app01
WAR on the restored VM: 03ab3c83afc5fad7...
WAR in the repo:        03ab3c83afc5fad7...
```

The WAR checksum on the rebuilt machine matches the repo exactly, so the bytes
came back intact rather than merely coming back.

## What the drill taught me

**Two recovery paths, and they cover different things.** The **machine** comes
from the cloud image plus Ansible. The **application content** comes from the
backup. Neither alone is a recovery plan, and the 348 s figure is dominated by
the first path.

**The backup scope is the deployment, not the machine.** The backing-up tree was
`/var/lib/tomcat10/webapps`, so Tomcat's own default `ROOT` application is not in
it. After the restore, `/labapp/*` works and `/` does not. That is correct for
this design - the proxy only needs the application - but it is a scope decision
worth stating out loud rather than discovering during an incident.

**The backup contains a Tomcat artifact.** The five archived files are
`labapp.war`, `labapp/health.jsp`, `labapp/work.jsp`, `labapp/WEB-INF/web.xml`
and `labapp/META-INF/war-tracker`. That last one is Tomcat's own deployment
tracker, generated by Tomcat, not written by me. It is harmless here and it made
the verification identical on both machines, but a stricter backup would exclude
generated metadata so that a restore cannot confuse a redeployment.

**In this lab the backup is not the only copy.** The WAR is also in git, so the
playbook alone restored a working service in 348 s. The backup proves the
independent path works, but for a truer test of "the backup was all I had", the
application would need state that git does not hold - a database, uploaded files,
unmanaged config. Saying this is more useful than implying the backup saved the
day.

## Reproducing

Steps 2 and 3 are safe and repeatable at any time. Step 1 is the only
irreversible action in this project; it is safe here only because the backup is
already off the VM and verified, and because `create-vms.sh` rebuilds the machine
from a cloud image.
